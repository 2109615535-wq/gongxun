# MCU—香橙派双摄像头通信协议 V1（设计稿）

本文供 MCU 与视觉程序双方实现使用；目前只设计协议，尚未接入固件。

## 1. 分工与连接

- MCU：比赛流程、轮速闭环、运动学、里程计、夹爪动作；根据视觉误差决定如何运动。
- 香橙派：两路摄像头采集、检测、跟踪、标定与坐标转换；回传识别结果。
- 两个摄像头连接香橙派，共用一条 MCU 通信链路，不传图片。
- 初版使用 3.3 V TTL UART，115200 bit/s、8 数据位、无校验、1 停止位，无流控。TX 接对方 RX，两端共地。
- 工程 USART2 已用于 IMU，UART5 已用于遥测；建议使用 USART3：MCU PC10=TX、PC11=RX。代码未发现其业务占用，但需核对实际板子是否引出、是否连接了其他硬件。香橙派串口引脚由具体型号确定。

## 2. 坐标与单位

| 数据 | 定义 |
| --- | --- |
| 高位摄像头结果 | BODY 坐标：以车体中心为原点，X 向右，Y 向前，随车体旋转 |
| 低位摄像头结果 | GRIPPER 坐标：以夹取对准点为原点，X 向车右，Y 向车前；表示目标相对夹取对准点的误差 |
| 距离 | cm，小数点后两位；MCU 可用 float 保存 |
| 航向角 | 度，顺时针为正；STATE 中为相对最近一次里程计归零的累计角度，可超过 360° |
| 时间 | ms |
| 置信度 | 整数 0～1000，例如 920 表示 0.920 |

摄像头自身的像素坐标、镜像、安装偏角、安装位置和比例由香橙派处理。LOW 的 Y 正方向不是图像的默认向下方向。

**坐标必须有真实标定依据。** 对固定地面/固定夹取平面，可通过标定与平面映射得到 cm；单目对未知高度物体不能仅靠像素直接确定真实距离。如果暂时只有像素，先补标定或另行约定像素协议，不能把像素填进本协议的 cm 字段。

高位“看全局”只描述视野，不表示已得到场地绝对定位。当前 OBS 是相对坐标；STATE 的 X/Y 是相对最近归零点的固定坐标，与 BODY 坐标不同。

## 3. 帧格式

```text
$1,TYPE,session,seq,字段1,字段2,...*CCCC\r\n
```

- ASCII 编码，无空格；类型大写。`1` 是协议版本。
- `$` 为帧头，`,` 分隔字段，`*` 后是 4 位大写十六进制 CRC，最后是实际的 CR LF 两个字节。
- `session`：MCU 分配的非零 uint32 会话号，每次 MCU 启动或重新建立连接时更换，可用硬件随机数或持久化计数器生成；不得固定写死。只有启动待连接的香橙派 HB 可以为 0。
- `seq`：uint16，各发送端独立编号，每发送一条新帧加 1，65535 后回到 0；命令重发保留原编号。两个方向出现相同 seq 是正常的。
- 整数用十进制；浮点字段仅允许 `-123.45` 形式，不允许指数、NaN、Inf 或空字段。正值不加 `+`。
- 一帧含帧头和结束符最多 192 字节，接收缓冲至少 193 字节以容纳字符串结尾。超过长度丢弃；收到新 `$` 重新开始；残帧超过 100 ms 丢弃。
- 先检查 CRC，再检查版本、类型、字段个数、范围、session 和 task_id；整帧通过后才一次性更新结果。
- CRC 不正确直接丢弃；未知版本不回应。合法当前会话中的未知类型可忽略。不可仅依赖一次串口接收恰好对应一帧。

### CRC 约定

CRC-16/MODBUS：初值 `0xFFFF`，反射多项式 `0xA001`，最终不异或。覆盖 `$` 之后、`*` 之前的全部 ASCII 字节，包含版本和逗号，不含 `$`、`*`、CRC 文本与 CR LF。

结果按数值写成 4 个十六进制字符，例如 `4B37`；这里不是 MODBUS 二进制低字节在前的传输格式。标准自检：`123456789` → `4B37`。

```python
def crc16(data: bytes) -> int:
    crc = 0xFFFF
    for byte in data:
        crc ^= byte
        for _ in range(8):
            crc = (crc >> 1) ^ 0xA001 if crc & 1 else crc >> 1
    return crc

def pack(payload: str) -> bytes:
    data = payload.encode("ascii")
    return b"$" + data + f"*{crc16(data):04X}\r\n".encode("ascii")
```

## 4. 消息总表

下表只列公共头 `$1,TYPE,session,seq,` 后面的字段，不含 CRC 与结束符。

| TYPE | 方向 | 后续字段 | 频率/响应 |
| --- | --- | --- | --- |
| HELLO | MCU→派 | 无（seq 后直接接 `*`） | 建立会话，需 ACK |
| TASK | MCU→派 | `task_id,mode,camera_mask,class_id` | 任务变化时发送，需 ACK |
| OBS | 派→MCU | `task_id,camera,status,track_id,class_id,dx,dy,confidence,in_grip,age_ms` | 每启用摄像头最多 20 Hz，无 ACK |
| STATE | MCU→派 | `task_id,origin_id,x,y,yaw,step,grip` | 10 Hz，无 ACK |
| HB | 双向 | `uptime_ms,camera_ready_mask,task_id` | 5 Hz，无 ACK |
| ACK | 派→MCU | `ack_seq,code,task_id` | 立即回应 HELLO/TASK |

### HELLO 与 ACK

香橙派启动后不运行旧任务，每 200 ms 发送 session=0、task_id=0 的 HB。MCU 收到后启动握手；已有握手进行中时不因重复 HB 重建会话。

MCU 发送新 session 的 HELLO；派清空旧任务和视觉缓存，保存该 session，回应 ACK，ACK 的 task_id=0。重复的同一 HELLO 只重发 ACK，不清空已经运行的新任务。

MCU 收到匹配 session 和 ack_seq、code=0 的 ACK 后才发送 TASK。双方建立会话后拒绝其他 session 的业务帧。正常活动期间不会无故发送新 session 的 HELLO。

ACK 的 `code`：0=接受并已切换任务，1=字段/范围错误，2=请求的摄像头未就绪，3=模式或类别暂不支持。拒绝时 task_id 回显请求中的编号，原任务保持不变。HELLO 的 task_id 始终为 0。

**ACK 不表示运动或抓取完成。** 本版香橙派不负责执行机械动作，因此无需机械动作 DONE 消息。

### TASK：MCU 指定看什么

| 字段 | 取值与意义 |
| --- | --- |
| task_id | uint32，非零；每个新任务/阶段递增，同一会话不复用；接近溢出时先重建会话。无任务为 0 |
| mode | 0=停止视觉任务，1=搜索并锁定目标，2=近距离对准，3=观察夹爪区域 |
| camera_mask | 1=高位，2=低位，3=同时启用；mode=0 时必须为 0 |
| class_id | 0=任意/不限制类别，1～255=双方另行登记的比赛目标类别；mode=0 时为 0 |

mode=2/3 要求启用低位摄像头。启用两路时每路单独回传 OBS，不需要等待另一摄像头同帧完成。mode=0 同样使用新的非零 task_id，ACK 后不再发送 OBS。

香橙派收到有效新任务后切换处理上下文，丢弃旧任务在处理中的结果，不能把旧图像结果换个新 task_id 发送。MCU 发出新任务时立即清除本地旧视觉有效标志；ACK 成功后才采用该新任务结果。

一个搜索任务内锁定一个目标，不能每帧随意切换最近的物体。丢失后先报告 status=0；初版重新选目标由 MCU 下发新 task_id 触发。

### OBS：两路摄像头的统一结果

| 字段 | 取值与意义 |
| --- | --- |
| task_id | 必须等于 MCU 当前已确认的任务 |
| camera | 1=高位，使用 BODY 坐标；2=低位，使用 GRIPPER 坐标 |
| status | 0=无合格检测，1=有检测且 cm 坐标有效，2=有检测但仅能提供类别/夹爪区域判断，cm 坐标无效 |
| track_id | uint16，1～65535 表示当前任务、当前摄像头下的跟踪编号；无结果时为 0 |
| class_id | 实际识别类别；0=未知/未分类；指定类别任务中不匹配的结果必须 status=0 |
| dx,dy | cm，范围 -10000.00～10000.00；目标相对指定原点的位置/对准误差 |
| confidence | 0～1000；有效性还需由 MCU 按业务阈值判断 |
| in_grip | 0=未知/不适用，1=目标可见但在约定夹爪区域外，2=目标可见且在区域内；高位必须为 0 |
| age_ms | uint16，图像采集到提交串口发送的耗时；65535=无法确定，禁止用于控制 |

status=0 时，track_id/class_id/dx/dy/confidence/in_grip 全填 0，age_ms 仍对应本次处理的图像。status=2 时 dx/dy 填 0，其他字段仍可有效；MCU 严禁用此时的 0 坐标认定已经对准。不得重复发送上一帧坐标并保持 status=1。相机故障与未见目标通过 HB 就绪位和数据超时进一步区分。

高位和低位的 track_id 各自独立；相同数字不保证是同一物体。跨相机对应关系由视觉算法实现，不能由 MCU 按编号直接认定。

in_grip=2 仅表示视觉上位于夹爪区域，不能证明已经夹紧、承重或不会掉落。mode=3 可以使用 status=2 的新鲜高置信度低位结果判断区域可见性；运动对准必须使用 status=1。状态 2 也允许高位只报告识别类别，此时 in_grip 必须为 0。

### STATE 与 HB

STATE 的 task_id 为当前已确认任务，无任务为 0。origin_id 为 uint16，每次里程计归零加 1，回绕允许；x/y 为里程计固定坐标 cm，yaw 为累计顺时针度数，均保留两位小数，允许绝对值不超过 1000000。step 为 uint16 业务阶段编号，grip 为 0=未知、1=张开、2=闭合、3=动作中；无传感器时只能表示机构命令/状态，不能表示可靠抓取成功。

HB 的 uptime_ms 是发送方启动以来的 uint32 毫秒计数，允许回绕，不代表双方时钟同步；camera_ready_mask：bit0=高位正常、bit1=低位正常，MCU 固定填 0。香橙派仅在设备采集正常且最近 500 ms 有新图像时置相应位，停用检测任务不必关闭采集。task_id 回报当前活动任务，停止或无任务为 0。

MCU 判断香橙派任务状态时忽略 TASK 切换握手期间的短暂 task_id 差异；ACK 成功后持续不一致则停止使用视觉并重建会话。

## 5. 重试、有效期与异常处理

- HELLO/TASK 一次只允许一个命令等待 ACK。300 ms 未收到 ACK 重发，最多重发 3 次。仍失败进入待连接状态，之后每秒重新尝试握手；不得继续依赖未确认的任务。
- 重发必须保留 session、seq 和原字段。派缓存最近 32 条可靠命令的原内容与 ACK，至少保留 2 s；收到重复命令只重发原 ACK。同一 session/seq 却内容不同作为协议错误丢弃。
- OBS/STATE/HB 不重发、不逐包确认。高低摄像头各保留一个最新 OBS，不能排队依次执行历史结果。
- OBS 对每路摄像头单独比较 seq：uint16 差值在 1～32767 才更新，0 为重复，其余为旧包。重建会话或切换任务后清除比较基准。此规则不用于过滤可靠命令重试。
- `age_ms` 应使用采集时间戳计算，尽可能在提交 serial.write 前才填写，不能只填写推理时间。香橙派限制串口发送队列滞留不超过 20 ms，过期视觉包直接丢弃；无法约束时本版不支持运动中视觉闭环。
- 初版暂定视觉控制门限：`age_ms + 20 ms发送排队预算 + 本帧串口传输时长 + MCU收到后的等待时间 <= 150 ms`；192 字节在本波特率下约需 16.7 ms。MCU 收到后还需检查 camera 就绪、status、任务和类别，以及业务置信度阈值（初始建议 800）。实际门限要结合模型帧率和控制试验调整。
- 某路启用摄像头连续 200 ms 没有新合格 OBS，清除该路控制有效标志；收到 status=0 时立即清除，status=2 立即清除位置控制有效标志。OBS 正在更新但过期或置信度不足，也不能继续沿用旧坐标。
- 任意一端 1 s 未收到对方的合法当前会话 HB，判定链路断开。派停止活动任务并改发 session=0 的 HB；MCU 清空视觉结果并重建会话。收到派 session=0 的 HB 也表示派已重启/退出旧会话，需要重新握手和重新下发任务。
- 依赖视觉的运动阶段遇断链、相机未就绪或结果失效，应退出该次视觉运动并将底盘速度降至 0，夹爪保持当前命令。恢复通信后由业务状态机重新发任务，不能自动执行缓存中的运动。其他自主流程的失效策略由业务层另行决定。
- 没有相机新图像时不能通过反复发送同一检测结果刷新有效期；串口中禁止混入普通日志，调试信息走另一串口或香橙派终端。

本版使用相对 age 和保守延迟预算，没有做到精确时钟同步/采集时刻位姿插值。高速旋转时暂不做视觉精确对准：例如 600°/s 下 50 ms 就产生 30° 的观测滞后。先停车或低速识别。未来做运动补偿、视觉定位或 EKF 更新时，增加同步时间戳、测量坐标系与协方差，不能将此处的结果直接当成当前时刻的绝对位置。

## 6. 可直接核对 CRC 的报文

以下每一行结尾均需发送实际 CR LF；代码块为了阅读不显示这两个字符。示例省略部分 ACK/HB 等中间交互，各方向 seq 独立。

MCU 建立会话，派回应：

```text
$1,HELLO,13579001,1*7531
$1,ACK,13579001,1,1,0,0*5CE5
```

MCU 请求高位搜索任意类别，派接受并报告目标在车右 12.50 cm、车前 65.00 cm，置信度 0.920，图像已耗时 35 ms：

```text
$1,TASK,13579001,2,1001,1,1,0*7665
$1,ACK,13579001,2,2,0,1001*CA4C
$1,OBS,13579001,3,1001,1,1,7,0,12.50,65.00,920,0,35*1A10
```

MCU 切到低位对准任务；派在对应 ACK 成功后报告目标相对夹取对准点偏右 1.20 cm、偏前 2.40 cm，位于夹爪区域外：

```text
$1,TASK,13579001,3,1002,2,2,0*B51F
$1,OBS,13579001,4,1002,2,1,3,0,1.20,2.40,950,1,28*B1B2
```

随后低位未见可用目标：

```text
$1,OBS,13579001,5,1002,2,0,0,0,0.00,0.00,0,0,30*E26B
```

派心跳表示两路相机正常、活动任务 1002；MCU 回传里程计位置 X=10、Y=50 cm，顺时针 30°，业务第 4 阶段，夹爪状态未知：

```text
$1,HB,13579001,6,123456,3,1002*C92F
$1,STATE,13579001,4,1002,0,10.00,50.00,30.00,4,0*44C6
```

## 7. 业务使用顺序与实现边界

1. MCU/派握手；MCU 发高位 SEARCH 任务。
2. MCU 根据 BODY 下的 dx/dy 接近目标。动作仍由底盘自身控制循环执行。
3. 接近后 MCU 换新 task_id 发低位 ALIGN；用 GRIPPER 下的 dx/dy 缓慢对准。
4. 误差连续多帧满足夹取范围后停车，MCU 控制夹爪闭合。
5. MCU 换新 task_id 发低位 VERIFY，判断夹爪区域的目标可见性；抓取可靠性还需结合机构反馈或离地后的持续观察。
6. 确认本阶段完成后，由 MCU 进入后续路线/动作。

先做握手、单路检测和超时停车，再加入双路切换、目标锁定和夹爪判断。目标类别编号、低位夹取对准点/区域、允许误差与置信度阈值需由两端在实测后共同登记，当前不猜测具体赛题类别。

115200 8N1 单方向理论上限约 11520 字节/s；两路各 20 Hz、按每帧 100 字节估算约 4000 字节/s，再加心跳仍有余量。最坏长度 192 字节时两路共约 7680 字节/s，不应再向同一链路灌入图片/日志。

MCU 后续可增加 vision_protocol.c/.h：串口中断只收字节到环形缓冲，主循环/调度任务里切帧、校验和更新两个结果结构体。现有 HAL_UART_RxCpltCallback 在 hdz601.c 中统一分发 USART2/UART5；接入 USART3 时应扩充分发，不得重复定义 HAL 回调，也不应在串口中断里运行 PID、body_move 或夹爪流程。
